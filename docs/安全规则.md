# Spring Nest 安全规则

## 概述

Spring Nest 采用 Supabase 作为后端服务，通过 Row Level Security (RLS) 实现数据隔离，确保每个用户只能访问自己的数据。本文档定义了项目的安全规则和最佳实践。

## Row Level Security (RLS) 策略

### 核心原则

**所有表必须启用 RLS。** 没有例外。

每条 RLS 策略的核心逻辑: `auth.uid() = user_id`

即: 当前登录用户的 ID 必须与数据记录的 `user_id` 字段匹配。

### profiles 表

| 操作   | 策略                             | 说明              |
| ------ | -------------------------------- | ----------------- |
| SELECT | 用户可以读取自己的 profile       | `auth.uid() = id` |
| UPDATE | 用户可以更新自己的 profile       | `auth.uid() = id` |
| INSERT | 由触发器自动创建，不允许手动插入 | 仅触发器可插入    |

### favorites 表

| 操作   | 策略                   | 说明                   |
| ------ | ---------------------- | ---------------------- |
| SELECT | 用户可以读取自己的收藏 | `auth.uid() = user_id` |
| INSERT | 用户可以添加收藏       | `auth.uid() = user_id` |
| DELETE | 用户可以删除自己的收藏 | `auth.uid() = user_id` |

### game_scores 表

| 操作   | 策略                                  | 说明                   |
| ------ | ------------------------------------- | ---------------------- |
| SELECT | 用户可以读取自己的分数                | `auth.uid() = user_id` |
| INSERT | 用户可以提交分数                      | `auth.uid() = user_id` |
| UPDATE | 用户可以更新自己的分数                | `auth.uid() = user_id` |
| 排行榜 | 所有人可读取排行榜数据 (不含 user_id) | 通过视图或函数实现     |

### user_settings 表

| 操作   | 策略                    | 说明                   |
| ------ | ----------------------- | ---------------------- |
| SELECT | 用户可以读取自己的设置  | `auth.uid() = user_id` |
| INSERT | 用户可以创建设置 (首次) | `auth.uid() = user_id` |
| UPDATE | 用户可以更新自己的设置  | `auth.uid() = user_id` |

### tool_usage 表

| 操作   | 策略                       | 说明                   |
| ------ | -------------------------- | ---------------------- |
| SELECT | 用户可以读取自己的使用记录 | `auth.uid() = user_id` |
| INSERT | 用户可以记录使用行为       | `auth.uid() = user_id` |

## 排行榜安全

排行榜需要特殊处理: 用户可以查看所有人的高分，但不能看到其他用户的 `user_id`。

实现方式:

1. 创建一个 `leaderboard_view` 视图，只暴露 `game_slug`、`score`、`username`（来自 profiles）
2. 对视图设置 RLS: 所有已认证用户可读取
3. 前端通过视图查询排行榜，而非直接查询 `game_scores` 表

## API 密钥管理

### 两种密钥

| 密钥类型         | 环境变量                    | 权限                                | 安全级别          |
| ---------------- | --------------------------- | ----------------------------------- | ----------------- |
| Anon Key         | `VITE_SUPABASE_ANON_KEY`    | 受 RLS 限制，只能操作当前用户的数据 | 可公开 (前端使用) |
| Service Role Key | `SUPABASE_SERVICE_ROLE_KEY` | 绕过 RLS，完全访问所有数据          | **绝对保密**      |

### 密钥使用规则

1. **前端只使用 Anon Key**
   - Anon Key 可以安全地嵌入前端代码
   - 所有操作受 RLS 保护，用户无法越权

2. **Service Role Key 只在服务端使用**
   - 仅用于管理后台、数据迁移、定时任务等
   - **绝不能**出现在前端代码、Git 仓库或客户端可访问的位置
   - 存储在服务端环境变量中

3. **密钥轮换**
   - 如果怀疑密钥泄露，立即在 Supabase Dashboard 轮换
   - 更新所有使用该密钥的环境变量

## 环境变量安全

### 必需的环境变量

```env
# Supabase 配置 (前端可用，受 RLS 保护)
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIs...

# Supabase Service Role Key (仅服务端，绝不暴露)
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIs...
```

### 环境变量规则

1. **`.env` 文件不提交到 Git**
   - `.gitignore` 已包含 `.env` 和 `.env.local`
   - 只提交 `.env.example` 作为模板

2. **Vercel/Netlify 环境变量**
   - 在部署平台的 Dashboard 中配置
   - 区分 Production / Preview / Development 环境

3. **Vite 环境变量前缀**
   - 只有 `VITE_` 前缀的变量会暴露给前端
   - `SUPABASE_SERVICE_ROLE_KEY` 没有 `VITE_` 前缀，不会被打包到前端

## CORS 配置

### Supabase CORS 设置

在 Supabase Dashboard → Settings → API 中配置允许的来源:

```
# 生产环境
https://your-domain.com
https://www.your-domain.com

# Vercel 预览环境
https://your-project.vercel.app

# 本地开发
http://localhost:3000
http://localhost:5173
```

### 规则

1. **不要使用 `*` 通配符** — 明确列出允许的域名
2. **生产环境只允许正式域名** — 不要包含 localhost
3. **预览环境单独配置** — Vercel 每次部署会生成不同的预览 URL

## 密码安全

### 密码要求

| 规则     | 说明                                |
| -------- | ----------------------------------- |
| 最小长度 | 6 个字符 (Supabase 默认)            |
| 建议长度 | 8 个字符以上                        |
| 复杂度   | 建议包含大小写字母和数字            |
| 存储方式 | Supabase Auth 自动处理哈希 (bcrypt) |
| 传输方式 | HTTPS 加密传输                      |

### Supabase Auth 密码配置

在 Supabase Dashboard → Authentication → Settings 中:

- **Minimum password length**: 6 (或更高)
- **Enable email confirmations**: 建议生产环境开启
- **Enable phone confirmations**: 按需开启

## 认证安全

### Session 管理

- Supabase 使用 JWT (JSON Web Token) 管理会话
- JWT 存储在 `localStorage` 中
- 默认过期时间: 1 小时 (可配置)
- 过期后自动使用 Refresh Token 刷新

### Auth Redirect URLs

在 Supabase Dashboard → Authentication → URL Configuration 中配置:

```
# Site URL
https://your-domain.com

# Redirect URLs (允许的回调地址)
https://your-domain.com/**
https://your-domain.com/auth/callback
http://localhost:3000/**
http://localhost:3000/auth/callback
```

## 数据验证

### 前端验证

所有用户输入在发送到 Supabase 之前必须经过前端验证:

| 数据         | 验证规则                                  |
| ------------ | ----------------------------------------- |
| 邮箱         | 格式校验 (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) |
| 密码         | 长度 >= 6                                 |
| 用户名       | 长度 2-20，不含特殊字符                   |
| 收藏 item_id | 必须是已知的游戏/工具 ID                  |
| 游戏分数     | 必须是正整数                              |

### 后端验证 (RLS)

RLS 策略是最后一道防线:

- 即使前端验证被绕过，RLS 也会阻止非法操作
- `CHECK` 约束确保数据类型和范围正确
- `FOREIGN KEY` 约束确保引用完整性

## 安全检查清单

部署前请确认:

- [ ] 所有表已启用 RLS
- [ ] 每个表都有正确的 SELECT/INSERT/UPDATE/DELETE 策略
- [ ] RLS 策略使用 `auth.uid() = user_id` 模式
- [ ] Service Role Key 未出现在前端代码中
- [ ] `.env` 文件未提交到 Git
- [ ] CORS 只允许信任的域名
- [ ] Supabase Auth 配置了正确的 Redirect URLs
- [ ] 密码最小长度 >= 6
- [ ] 生产环境开启了邮箱确认
